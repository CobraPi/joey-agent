The production workspace is organized as Overview → Define → Design → Break down → Build → Review. spec.md, plan.md, and tasks.md appear inside those stages as source indicators and escape hatches, not as knowledge the user must possess upfront.

The core thesis

Spec Kit already produces excellent structured documents. The problem isn't the content — it's that a wall of markdown hides its own structure. The IDE's job is not to replace markdown. It's to make the structure that is already in the markdown visible, navigable, and editable.

Markdown is the database. The IDE is the query engine.
Every file under specs/###-feature/ stays the single source of truth, byte-for-byte compatible with the CLI. The IDE parses it into a semantic graph, renders projections of that graph, and writes reviewed patches back through verified byte anchors. CLI-compatible identity and binding sidecars remain supported; private display preferences stay outside the repo. A teammate on the CLI never needs the GUI to continue the workflow.

Three pillars

Pillar 1

The Stage Bar

One compact, always-visible stage indicator showing where the feature is and what comes next. Command detail expands only when needed. It replaces “which slash command do I run now?” with one deterministic next action and actionable gates.

Pillar 2

The Meaning Layer

Each markdown construct is rendered with the visual primitive that matches its semantics — priorities become rails, Given/When/Then becomes a flow, success criteria become metric cards, tasks become a board. Never a generic markdown blob.

Pillar 3

The Trace

Constitution → Story → Requirement → Task → File → Checklist as one connected graph. Selecting any node highlights everything it touches. Orphans (a requirement no task implements) become visually impossible to miss.

What "100% of the workflow in the UI" actually requires

Five capabilities must all be present, or the user drops back to the terminal and the IDE fails:

CapabilityWhy it's load-bearing
InitiateEvery one of the ten speckit.* commands is launchable from the UI with typed inputs — no free-text command memorization.
ObserveStreaming agent output, tool calls, and file writes render live. A run that looks frozen is the #1 reason users abandon a GUI for a terminal.
AnswerThe agent asks clarifying questions mid-run. These must surface as first-class interactive cards, not buried log lines. This is the speckit.interaction.respond path.
EditDirect manipulation of generated artifacts with round-trip safety. If the user must open VS Code to fix a typo, the loop is broken.
ApproveDiff-first review with hunk-level accept/reject before anything touches the working tree. Trust is the currency; staged-by-default buys it.

The failure mode we are designing against

Anti-pattern

A two-pane app: file tree on the left, rendered markdown on the right, "Run" button on top. This is a markdown viewer with a shell attached. It renders markdown, not meaning. Users still can't see coverage, priority, dependencies, or what to do next — so they keep the terminal open beside it and the IDE becomes decoration.

Target

A tool where the visual is the primary artifact and raw markdown is the escape hatch — available on ⌥M for any node, never required. Users reason about the feature in boards, graphs, and metric cards, and only drop to text when they want to.

The dashboard is a projection of CLI-compatible project files, driven by the agent over the existing gateway. Three layers, one rule: repo state must remain readable and operable without the IDE.

Three layers

Layer 1 — Truth

Markdown + CLI-compatible sidecars + git. Written only by the agent through reviewed patches or by the user's accepted edits. The IDE preserves unknown syntax and never rewrites an untouched range.

spec.mdplan.md tasks.mdresearch.md data-model.mdcontracts/ checklists/constitution.md .speckit-feature.yml.specify/bindings.yml*

* Shared binding mode only; the UI previews this working-tree change before enabling it.

Layer 2 — Meaning

A lossless concrete syntax tree plus a derived semantic graph. Every node keeps its UTF-8 byte range, expected source bytes, document revision hash, and a structural fingerprint. Those checks—not reparsing alone—make visual editing safe.

Node {
  id:      "FR-014"
  kind:    "requirement"
  file:    "spec.md"
  anchor:  { byteStart: 8172, byteEnd: 8268 }
  revision: "sha256:4d1…"
  expected: "- **FR-014**: Users MUST…"
  fingerprint: "requirements/FR-014"
  props:   { modality: "MUST", … }
  edges:   [ "US2", "T034", "CHK007" ]
}
Layer 3 — Overlay

Private IDE state that must never dirty the working tree. Lives in profile-scoped SQLite, keyed by repo + branch. Shared binding metadata is a separate, explicit repo-sidecar mode. Losing the private overlay costs convenience, never authored work.

  • Run history & attempt transcripts
  • Private feature ↔ branch bindings, drift state
  • Anchored comments & review feedback
  • Board positions, filters, panel layout

Clarify queue — turning unknowns into a workflow

Every [NEEDS CLARIFICATION] marker across all artifacts is collected into the persistent Agent Activity Center. Answering creates a proposed source patch; the user previews and accepts it under the same staged-change policy as every other agent edit.

OPENspec.md : 214FR-016
What debounce interval should board edits use before syncing to disk?
Context: FR-016 requires write-back but leaves timing unspecified. Affects T034 and the drift detector.
Choose an answer
Why this beats the CLI
  • Batched, not serial. The terminal asks one question at a time and blocks. The queue shows all open unknowns at once, so the user answers in one sitting.
  • Contextual. Each card carries its source line, the requirement it belongs to, and what downstream work it blocks.
  • Resumable. Close the tab mid-answer; the queue persists in the overlay store and the run reattaches via speckit.run.attach.
  • Auditable. Accepted decisions are recorded with timestamp, author, and the reviewed patch.
  • Zero-typing path. Multiple choice with an agent-recommended default means the common case is one click.
Proposed patch preview: - **FR-016**: System MUST sync board edits back within 300 ms of the last keystroke.

Round-trip editing

Visual editing is only safe if every widget knows exactly which bytes it owns. This is the contract that makes the whole concept viable rather than a demo.

The lossless patch contract

Six rules
  • Parse losslessly. A concrete syntax tree preserves whitespace, comments, unknown extensions, and untouched bytes.
  • Use one anchor contract. Each node records UTF-8 {byteStart, byteEnd}, expected source bytes, and a structural fingerprint.
  • Guard every write. Before patching, verify the document revision hash and expected bytes still match the current file.
  • Edits are surgical. Changing a story title rewrites only that heading line — never the whole file. Untouched bytes stay byte-identical.
  • Apply transactionally. Patch a temporary buffer, parse and validate it, then atomically replace the file and retain undo history.
  • Never guess through drift. Any revision or source mismatch routes to three-way merge instead of attempting write-back.
Three editing depths — always available
1 · Structured default
Typed form fields per node kind. Priority is a select, Given/When/Then are three inputs, modality is a toggle. Impossible to produce malformed markdown.
2 · Inline markdown ⌥M
CodeMirror on just that node's range, with markdown highlighting. For when the structure doesn't fit what you want to say.
3 · Whole file ⌥⇧M
Full CodeMirror on the raw document. The escape hatch that guarantees the IDE never becomes a cage.

Conflict handling

Three writers can touch the same file: the user in the UI, the agent mid-run, and the outside world (CLI/editor/git). The resolution order is fixed and never silent.

SituationBehaviour
User edits during a runThe edited node locks. Agent output for that node is diverted to the review pane instead of applied — the user's intent is never clobbered mid-thought.
External change on diskFile-watch triggers reparse. A revision-hash mismatch blocks the write. If the user has unsaved edits, a three-way merge card compares base, current file, and proposed patch at semantic-block level.
Anchor no longer resolvesThe node degrades to read-only with a "structure changed — reopen" prompt. It never guesses a new range.
Malformed markdownPartial render: parseable nodes get widgets, the rest falls back to raw text. The view never blanks out on a bad file.
Patch validation failsNo file is replaced. The proposed buffer and parser diagnostics remain available for repair or raw review.
User wants to reverse an editEvery accepted visual edit has an undo entry containing the verified inverse patch and originating semantic action.

Agent runs & review

The run experience is where trust is won or lost. Two principles: never look frozen, and never touch the working tree without permission.

One persistent Agent Activity Center

Questions, requested permissions, proposed actions, live runs, failures, and review decisions share one chronological surface. Each item states whether it is a draft, derived event, or proposed repo patch.

Before run
  • Objective and expected outputs
  • Allowed tools and file scope
  • Validation commands and stop conditions
  • Token/time budget
During run
  • Current objective, tool, and affected file
  • Questions and permission requests
  • Checkpoint state and partial outputs
  • Cancel explains what is preserved
After run
  • Outcome and validation summary
  • Unresolved failures and partial success
  • Semantic diffs ready for review
  • Retry from checkpoint or rollback

  • Tool-call timeline, not a text log. Each read/write/search is a row with a state icon.
  • Progressive artifact preview. Tasks appear as chips as they stream — the board builds itself in front of you.
  • Elapsed time + phase label so a 90-second step reads as working, not hung.
  • Optimistic skeletons for the boards that are about to populate.
  • Reattach on reload. speckit.run.attach means closing the tab doesn't kill or lose the run.
  • Crash recovery banner. speckit.run.recover surfaces an interrupted attempt with resume / retry / discard.

Diff-first review

Everything the agent produces lands staged. The user accepts at hunk granularity — and because the IDE knows the semantic graph, hunks are labelled by what they mean, not just line numbers.

specs/004-visual-branch-ide/spec.md +14−2
Hunk 2 of 4 — adds requirement FR-016 under Functional Requirements
210- **FR-014**: Users MUST be able to toggle task completion.
211- **FR-015**: System SHOULD persist board filter state.
212- **FR-016**: System MUST sync board edits back within [NEEDS CLARIFICATION]
212- **FR-016**: System MUST sync board edits back within 300 ms of last keystroke.
213- **FR-017**: System MUST reparse affected anchors after each write-back.
214

The header "adds requirement FR-016" is the differentiator. Plain git diffs make reviewers reconstruct intent from line noise; a semantic diff states it. Accepting this hunk also clears the matching card from the Clarify queue and updates the coverage matrix — one action, consistent state.

Modern UI techniques in play

Each technique below is chosen because it solves a specific problem this workflow has — not because it's fashionable.

Semantic zoom

Three altitudes: Atlas (whole feature) → Board (one artifact) → Focus (one node + its markdown). Zooming changes information density, not just scale — cards reveal more fields as you descend. Solves: a 28 KB spec.md is unreadable at one altitude.

Command palette ⌘K

Every action, artifact, requirement, and task reachable by typing. Keeps CLI muscle memory intact — power users never lose speed by moving to a GUI, which is the usual reason they refuse to. Solves: GUIs feel slower than terminals.

Direct manipulation + optimistic UI

Drag a task between phases, drag a story to re-prioritize, or check a box. Local reorder is optimistic; any cross-boundary move pauses for a semantic-impact preview, dependency validation, and explicit confirmation. Every drag also has a Move menu and undo entry.

Progressive disclosure

Story cards show title + priority + coverage; a visible disclosure button expands rationale and scenarios; ⌥M reveals raw markdown. Nothing depends on hover and nothing is omitted—secondary detail is simply deferred.

Streaming & skeletons

Agent output renders token-by-token into the destination widget, with shimmer skeletons where content is still arriving. Solves: multi-minute LLM steps that otherwise look like a hang.

Focus + context highlighting

Selecting a node dims unrelated content across every open panel instead of navigating away. Solves: traceability requires seeing relationships, and navigation destroys the mental model.

Deterministic guidance

The "next action" is computed from artifact state by rules, never generated by a model. Reproducible, auditable, instant, and free. Solves: users don't trust — and shouldn't pay for — an LLM to tell them which button to press.

Anchored comments

Figma/Docs-style threads pinned to a semantic node, stored in the private overlay by default. Team sharing is an explicit server-backed mode, never implied by local storage. Anchors use semantic identity plus structural fingerprints and visibly detach when confidence drops.

Keyboard-first + a11y

Every drag has a Move menu equivalent; each graph has a relationship-table view; status changes use live regions; controls use native semantics and 44px mobile targets. State is always color + icon + text, with WCAG AA contrast tokens.

Context continuity

Every feature, node, run, and review state has a deep link. Selection, filters, scroll position, and staged status survive view changes and browser Back/Forward. Motion is optional and disabled under reduced-motion preferences.

Purpose-built responsive modes

Desktop supports graph authoring and multi-panel comparison. Tablet prioritizes structured forms and board review. Mobile focuses on status, questions, approvals, and diffs—not precision graph manipulation.

Deliberately rejected

Tempting ideaWhy it's rejected
WYSIWYG rich-text editingRound-trips markdown lossily. The moment a save reformats the whole file, CLI users get unreviewable diffs and abandon the tool.
Proprietary project databaseBreaks the git-native contract. Markdown must stay the single source of truth or the IDE forks the workflow instead of visualizing it.
LLM-generated "next step" hintsNon-deterministic, slow, costs tokens, and occasionally wrong about something the app can compute exactly.
Requiring terminal knowledgeRaw markdown remains a complete escape hatch inside the product, but users never need to know slash commands or leave the dashboard to finish the supported workflow.
Auto-applying agent editsOne bad overwrite on a real branch destroys trust permanently. Staged-by-default is non-negotiable.

The one thing to get right first
P0. If the lossless parser and optimistic-concurrency patch engine are solid, every widget after it is a small, independent, testable component and the phases can proceed in parallel. If P0 is shaky, every visual edit becomes a file-corruption risk and the whole concept collapses back into "a markdown viewer with a Run button".

Definition of done — the 100% test

The concept succeeds only if a user can do all of this without a terminal:

1Connect a repository, validate access, and initialize missing Spec Kit setup with a file preview
2Create or bind a feature branch and preview every identity/binding sidecar change
3Create or amend the constitution and see principles as gates
4Describe an outcome in plain language and generate a staged spec.md
5Answer clarifications as cards and review the resulting patches
6Generate and edit the design, resolving unknowns inline
7Generate tasks, reorder safely, and preview semantic impact for cross-phase moves
8Run analysis and repair every orphan or unverified requirement from the matrix
9Generate and complete quality checklists
10Scope agent permissions, run implementation, and observe files, tools, tests, and checkpoints
11Review semantic hunks, accept selectively, undo edits, and resolve conflicts
12Recover from a failed or interrupted run without losing drafts, answers, or staged changes
